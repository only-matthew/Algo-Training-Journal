## 方法与可测量性声明

- 数据来源：`logs/` 全量 `meta.json` 与正文文件、`curriculum/`、构建产物 `site/`、`git log`、`npm test`。
- 关键计算复用生产代码的归一函数（`scripts/curriculum.mjs#problemKey`），不自行发明题号口径。
- **本仓库没有任何使用埋点**：没有分析脚本、没有点击统计、Worker 也没有事件计数。因此"导出被点了几次""QQ 机器人被用了几次""某页面被看了几次"**无法测量**。本文所有"使用率"都是从**数据后果**反推的（例如"题面归档用过几次"看 `statementImages` 字段与仓库内是否存在对应文件），并已在各处注明口径。这一点本身是本次审计的第一个结论（见 P0-2）。
- 涉及时间的指标一律给**中位数**：均值被少数补录样本严重拉偏（例：廖夏记录时滞中位数 0.50 天、均值 3.61 天）。

验证基线：`npm test` 539 项全绿（462 + Worker 77）；`npm run build` 2.7 秒；产物 902 文件 23.9 MB。

## 一句话结论

**这个产品已经解决了"记不记得下来"，但还没解决"记下来干什么"。** 四个月里它在**横向上变得很宽**（题单 2857 行、标签 179 个、题面抓取、难度归一、活力指数），而在**纵向上没有变深**（`PRODUCT.md` 第一批"个人日常训练闭环"5 项里，4 项没有用户侧入口，1 项只做到节点级）。数据后果很直接：越靠"录入"的功能使用率越高（难度 99%、题号 93%、标签 69%），越靠"新增数据面"的功能使用率越低（题单完成率 4.9%、题面归档 0 次），而**唯一能证明记录有价值的东西——人写的心得——平均只有 88 字节，其中 21.6% 是空或占位符**。

**两条可直接用作产品决策的事实**：

1. **放进表单的字段就会被填**。2026-09-16 之后落地的四个字段，在之后的 24 条记录里采纳率是：

   | 字段 | 09-16 之前（170 条） | 09-16 及之后（24 条） |
   | --- | --- | --- |
   | `outcome`（完成结果） | 3% | **83%** |
   | `masteryStatus`（掌握自评） | 6% | **100%** |
   | `isMistake`（错题标记） | 6% | **100%** |
   | 代码正文 | — | 100% |

   之前覆盖率低**不是因为队员不想填，而是因为字段还没上线**。这条推翻了"这个队伍不爱记录细节"的假设。
2. **需要人额外判断"该不该用"的功能就不会被用**：复习状态默认 `none`，结果 91% 的记录从未进入复习队列；题面归档需要用户主动上传或依赖抓取，结果是 0 次。区别不在"填起来麻烦"，而在"要不要额外想一下"。

**这是本次审计最重要的一条**：题面抓取链路（1346 行代码 + 1137 行测试）把"把题目搬到站内"的摩擦力降到了接近零，但站内最终留下的、属于队员自己的东西只有 88 字节。

| --- | --- | --- |

### 1.5 活跃度在衰减，但衰减的不是记录质量

| 周（周一起） | 记录日 | 题目数 | 题/记录日 |
| --- | --- | --- | --- |
| 2026-07-20 | 13 | 14 | 1.08 |

- 8 月中旬两周是 `21/21`——**三名队员每天不落**。

- 但**单次记录的题数反而上升**（1.05 → 1.70）：他们从"每天记一题"转成了"每次训练/比赛批量记几题"。

**产品含义**：把"每天一条"当作成功指标会误判这个产品的健康度。真实的使用单位已经从**日**变成了**场次**。

### 1.6 协作：价值存在，但很薄

- 127 道唯一题里，**38 道（29.9%）被 ≥2 人做过**，只有 4 道三人全做过。
- 单飞比例：廖夏 54%、王梓豪 61%、郭一鸣 42% 的题只有自己做过。
- 队伍做过 127 道题，其中 **74 道（58.3%）** 出现在任一题单里。

**结论**：`全队同题记录`／`二刷对比` 有真实内容（38 道），不是空功能；但它是"等人点进去看"的被动价值，没有主动触达。

## 3. 计划 vs 交付 vs 使用

### 3.1 产品自己排的第一批计划：用户侧几乎没落地

[PRODUCT.md](PRODUCT.md) 的「第一批：个人日常训练闭环」是它自己认定的最高优先级：

| 计划项 | 实现情况 | 使用 |
| --- | --- | --- |
| 今日训练台（选专题 + 时间预算 → 今日清单） | **用户侧 0 入口**。后端 v2 已有 `GET /me/plans/:date`、`POST /me/plan-actions` 与 `recommendV1` 推荐（`lib/recommendations.mjs`、`workers/services/training-read.mjs`、`workers/oauth.mjs`），但唯一消费者 `lib/training-dashboard.mjs` 只被测试引用，`/training/` 路由已下线 | 无 |
| 快速记一题（只要求题目身份 + 结果，约半分钟） | **未实现**。`/submit/` 仍是全量表单（题名/题号/平台/难度/标签/描述/心得/代码/结果/自评/复习/附件） | — |
| 真正的重做与复习（重做时折叠旧题解、记录重做结果） | **部分**。有 `reviewStatus` + `reviewDue` + 单题 PATCH；无重做历史、无"折叠旧题解"、无重做结果记录 | 复习入队 **3.1%**（todo 6/194） |
| 能力卡（不同题目数 / 尝试次数 / 独立完成 / 提示依赖） | **节点级已上线**（`assessMastery` 已接入 `scripts/generate-data.js`，节点页显示五档状态/理由/置信度）；**个人级未实现**（没有"不同题目数/尝试次数/独立完成/提示依赖"的页面） | 记录级 `masteryStatus` 18% |
| 协作第一批（约赛 / 报名 / 补题 / 同题求助） | **未实现**（`contest-invite`、`help-request` 等标识符 0 命中）；现有协作能力只有同题聚合 | 同题协作率 29.9% |

同一份文档规划的顶层导航是「今天 / 学习 / 复习 / 队伍 / 我的」，实际线上导航是「首页 / 训练档案 / 复习 / 知识地图 / 标签」。

**这不是"计划没做完"，而是计划被换掉了**，且换掉这件事没有写在任何文档里。当前 `SPECIFICATION.md` 的自相矛盾、`PENDING-FEATURES.md` 的状态失真都是这个分叉的下游症状。

### 3.3 产物的内容质量：425 条 sitemap URL 里 180 条是标签页，139 条零记录

- 标签总数 179，其中 **139 个的 `recordCount = 0`**，全部进入 `sitemap.xml`，全部没有 `noindex`。
- 这些页面的独立内容基本只有"覆盖它的知识树节点"列表，其余是全站复用的外壳。
- **体积不是问题**：标签页 180 个共 10 MB / 知识树页 47 个共 5.8 MB，但 gzip 后单页只有 17 KB / 22.8 KB，传输正常。要处理的是**索引策略**，不是性能。
- **本地产物不清理**（不影响线上）：本机删除 `site/` 全量重建后，唯一未被引用的陈旧文件是 `assets/ink-mountains.png`（1.61 MB，实际使用的是 `.webp`）。根因是构建不清理 `site/`（`copyDirRecursive("src/assets", …)` 只复制不删，`removeUnlistedFiles` 只覆盖 `assets/js`）。**线上不受影响**——CI 每次全新 checkout 后构建，`site/` 从空开始——但它会让本地预览与体积统计出现偏差。详见 [§4 P2-3](#p2-3--本地产物卫生与索引策略)。

## 4. 产品级问题

### P0-1 · 投入最大的两个功能，使用率最低

**现状**：题单（3409 行源码 + 1271 KB 数据）完成率 4.9%；题面抓取/归档（1346 行源码 + 1137 行测试）被用了 8 次抓取、0 次图片、0 次 PDF。

**证据**：§2 投入产出账、§3.2、§1.2。

**影响**：

- **机会成本**：这两块合计 4755 行源码，是当前仓库最大的一笔工程支出；同期 `PRODUCT.md` 自己排在第一优先级的"今日训练台 / 快速记一题 / 重做复习"三项都没有用户侧入口。
- **维护成本**：题面链路绑定两个外部站点的解析器（`cf-html-v4`、`luogu-mirror-v3`、`luogu-atcoder-mirror-v1`），上游一改版就要维护，而收益是每天 0 次。
- **承诺失真**：README 用大量篇幅描述题面图片归档、镜像兜底、小书签，读者会以为这是核心能力。

**建议**：

### P0-2 · 产品定义了自己的成功指标，但一个都没有埋点

3. **前端匿名计数（可选，1 天）**：导出按钮、复习快捷按钮、标签芯片点击各打一个 `navigator.sendBeacon` 到 `/api/events`（不记身份、不记内容、可一键关闭）。**如果觉得 2/3 违反"队员自主、不考核"的产品原则，就只做 1，并接受导出/机器人长期不可测。**

### P0-3 · 复习闭环使用率 9%，而它是产品宣称的核心闭环

**现状**：`reviewStatus` 实测 `none` 159、字段缺失 17、`archived` 8、`todo` 6、`mastered` 4（历史值）；`reviewDue` 只有 4 条。**真正处于"待复习"状态的只有 6 条（3.1%）**，而首页的「今日复习队列」正是基于它。

**证据**：§1.2 字段表；`lib/learning-state.mjs` 的默认值 `REVIEW_STATUSES.NONE`。

**影响**：

- README 把"记录 → 复习 → 掌握"当作卖点，但默认路径下队列永远是空的，用户看到的是空状态而不是闭环。
- `PATCH .../records/:id`（单题复习命令）已实现且可靠，但它的入口几乎无人走到——**这是"功能做完了但没人用"的典型样本**，比"没做完"更值得警惕。

**建议**：

1. **默认入队**：保存时按信号自动设置 `reviewStatus = todo`、`reviewDue = +3 天`——`outcome ∈ {hinted, editorial, unfinished}` 或 `isMistake === true` 时自动触发，用户仍可改为 `none`/`archived`。这样队列立刻有内容，且不需要用户理解"复习状态"这个概念。
2. **给队列一个主动出口**：站点已有 Service Worker，却没有 `manifest.json`、没有 `push` 处理。QQ 主动推送自 2025-04-21 已被平台取消（README 已记录），**Web Push 是当前唯一能主动触达队员的合规通道**。加 PWA manifest + `push` 事件 + Worker 侧订阅存储 + 每日 Action 推送"今日到期复习"。
3. 与 `PENDING-FEATURES.md` 的边界一致：队列只作提示，**不设逾期问责、不做排名**。

### P1-1 · 产出端极薄：心得平均 88 字节，21.6% 是空或占位符

**现状**：194 条记录的心得平均 88 字节（约 30–40 个汉字）；占位/空 21.6%、<20 字 32.0%、≥20 字 46.4%。**这是持续缺陷而非历史遗留**：按月占位率 14%（7 月）→ 25%（8 月）→ 20%（9 月），没有下降趋势。

**证据（可直接复现）**：

- 写入端把空心得落盘成字面量：`workers/services/log-planning.mjs:43` 与 `workers/services/logs-v2.mjs:242` 的 `problem.takeaway || "未填写"`。
- 42/194 条 `N-takeaway.md` 全文就是 `未填写`（廖夏 19/79、郭一鸣 22/49、王梓豪 1/66）。
- 已经泄漏到用户可见处：成员页渲染 `<p class="record-summary">未填写</p>`；题目详情页「个人思考」渲染 `<div class="detail-prose"><p>未填写</p></div>`；实测 `buildSingleLatexDocument()` 会输出 `\subsection{题解}` 正文 `未填写`；构建产物中 **123 个文件、150 处**含该字面量。
- 代码已经在跟它搏斗：`scripts/generate-data.js:601` 不得不特判 `log.takeaway !== "未填写"`；而同一个字面量又是**合法的平台取值**（`lib/constants.mjs:21` 的 `PLATFORM_DEFAULT = "未填写"` 被 `lib/log-schema.mjs:131,181` 用作平台缺省值）——**同一个字符串既表示"平台没填"又表示"心得为空"**。

**影响**：产物、导出、SEO、搜索里都混入了无意义内容；任何"这条有没有心得"的判断都得靠字符串比较；这是全部使用率数据里最刺眼的一格（对比：题号 93%、标签 69%、难度 99%）。

**建议**：

1. **空就是空**：写入端写空文件或不写文件；读侧把"不存在/内容为空"当缺失。删掉 `generate-data.js` 的特判与两处 `|| "未填写"` 兜底；把平台默认值换成 `未知平台` 之类不冲突的词；加一条守卫测试禁止正文等于该字面量；一次性清空现存 42 个文件（它们无歧义）。
2. **把心得变成一等公民**：表单里给结构化提示（错因 / 卡点 / 关键转化 / 下次怎么做）；保存前心行为空时给一次**非阻塞**提醒；成员页把"我的复盘"做成可回看的列表。这是唯一能把 §1.3 的 88 字节变得有意义的杠杆。
3. 顺带修好判定：`lib/export-content.mjs:53`、`:416` 用的是 `if (log.takeaway)`，占位符会被判为有值并导出——修 1 之后自然消失。

## 8. 技术性建议（工程、发布与文档）

§4 是产品级问题；本节是与之配套的**工程侧**清单，来源是同一轮探索。产品结论说"该做什么"，本节说"做的时候地雷在哪"。编号 `T1–T6`，与 §4 的 `P0–P3` 分开索引。

| 编号 | 事项 | 成本 | 收益 |
| --- | --- | --- | --- |
| **T1** | Worker 与前端是两个独立发布通道，顺序靠人记 | M | 消除唯一一类"保存功能整体失效"的发布事故 |
| **T2** | 静态检查只查语法，未使用变量/未定义引用/死导入全部漏网 | S | 让 `npm run verify` 真正可信 |
| **T3** | `oauth.mjs` 同时是 HTTP 入口与领域库；Worker 反向依赖 `bot/` | M | 边界与文档一致，新人不会再放错文件 |
| **T4** | deploy 内部重复构建；PR 合并合计 3 次构建 / 2 次 Chromium 安装 | S | 直接减 CI 时间与失败面 |
| **T5** | 文档 447 KB / 21 篇 + README 52 KB，同一事实散落 4–5 处 | M | 消除"文档失真 → 返工"的复发路径 |
| **T6** | 目录契约有缺口，且与代码冲突 | S | 让"新文件放哪里"有唯一答案 |

### T1 · 发布链路：Worker 与前端是两个通道，顺序只靠文档约定

**现状**：前端由 GitHub Actions 自动发布（`.github/workflows/deploy.yml` 在 push 到 `main` 后构建 + 部署 Pages）；Worker 由维护者在本机 `npx wrangler deploy` 手工发布，**仓库里没有任何 workflow 部署 Worker**（`grep wrangler|cloudflare .github/workflows/*.yml` 无结果）。两者之间的版本兼容是**单向**的。

**证据**：

- `lib/log-schema.mjs:10` 与 `workers/services/logs-v2.mjs:208`、`:278` 都拒绝 `schemaVersion > LOG_SCHEMA_VERSION`，抛 `UNSUPPORTED_SCHEMA`（"不支持的日志版本，请更新客户端后重试"）。当前 `LOG_SCHEMA_VERSION = 6`。
- 因此**新前端 + 旧 Worker = 保存全部 422**，而**旧前端 + 新 Worker = 正常**。[HANDOFF.md](HANDOFF.md) 的多轮部署记录把"先 Worker 后前端"写成人工约定，并记录过一次由此产生的失败模式：新前端发 `schemaVersion: 6`、旧 Worker 对 `> 5` 一律 422，保存功能全线失效。
- 部署 Worker 需要逐条配置 7 个 secret（3 个 OAuth + 4 个 QQ），全部只能在本机用 `wrangler secret put` 完成，没有第二条路径。

**影响**：这是当前唯一一类能让**全部队员的写功能同时失效**的操作，而它的唯一防线是维护者记得顺序。它也不会被 CI 拦住——CI 只测代码，不测"线上 Worker 是哪个版本"。

**建议**（按性价比排序，任选其一即可显著降低风险）：

1. **把兼容变成契约并测进去**（首选，纯代码）：明确"Worker 必须同时接受当前版本与上一版本载荷"，为新旧两侧各加一条测试；把"旧 Worker 遇到更高版本"的行为从硬拒改为"降级读取 + 明确错误提示"。这样顺序不再重要。
2. **让机器保证顺序**：新增一个只在 `workers/**` 变更时触发的 workflow 部署 Worker，并让 Pages 的 deploy job `needs` 它。需要把 Cloudflare API token 放进仓库 secret。
3. **最低限度**：加部署后冒烟（匿名 `GET /api/session` 应 200、一次只读 v2 调用应返回结构），并在 README 里把"顺序约定"升级为"发布检查清单"。

### T2 · 静态检查只查语法，抓不到死导入与未定义引用

**现状**：`npm run check:syntax` 是 `npm run verify` 的第一步，但它的覆盖面只有**语法解析**。

**证据**：

- [check-syntax.mjs](scripts/check-syntax.mjs) 对 90 个源文件逐个执行 `spawnSync(node, ["--check", file])`，只判断退出码；`node --check` 只做解析，不解析引用。
- [jsconfig.json](jsconfig.json) 的 `compilerOptions.checkJs` 是 **`false`**——VS Code 的 TypeScript 服务同样不做 JS 检查。
- 仓库内没有 ESLint / Prettier / Biome 任何配置（`ls` 只有 `.editorconfig`、`.gitignore`、`jsconfig.json`）。

**影响**：未使用变量、未定义引用、写错名字的导入、死导入这一整类问题**只能靠 539 个单测偶然撞到**——只有当某个测试恰好 import 了那个模块才会暴露。[PROBLEM-AUDIT.md](PROBLEM-AUDIT.md) 第 3 条记录的 `scripts/generate-data.js` 中 `mergeTrainingDates` "已实现、已导入、从未被调用"（直到后续提交才真正接线），正是这一类的典型：它当时不是构建失败，而是靠人工通读才发现的。

**建议**：先只开两条规则（成本 S，改动面小、误报极低）：`no-unused-vars` + `no-undef`，加进 `npm run verify` 与 CI。等稳定后再按需加 `no-unreachable`、`eqeqeq`。**不必**一上来引入 Prettier 全量重排（会产生一个巨大的噪音 diff）。

### T3 · 职责边界：`oauth.mjs` 仍是"入口 + 领域库"，Worker 还反向依赖 `bot/`

**现状**：`PROBLEM-AUDIT.md` 第 14 条已经把日志规划拆到 `workers/services/log-planning.mjs`，但拆分只做了一半。

**证据**：

- [oauth.mjs](workers/oauth.mjs) 1215 行，既导出 HTTP 入口（`default`），又直接导出领域能力：`saveLog`、`readLog`、`deleteLog`、`summarizeDescription`、`assertLogVersionPlan`、`fetchCodeforcesAccepted`、`fetchLuoguProblems`、`fetchAtCoderAccepted`。其中抓取解析类能力（1346 行那一块的入口）与 HTTP 生命周期完全无关。
- [qq-bot.mjs](workers/qq-bot.mjs) 顶部 `import { fetchAccessToken, sendGroupMessage, chatCompletion } from "../bot/qq-bot.mjs"` 与 `from "../bot/qq-message.mjs"`——**Worker 依赖 `bot/`**。而 [REPOSITORY-STRUCTURE.md](docs/REPOSITORY-STRUCTURE.md) 的依赖图里 `bot/` 根本没有出现，表格对 `bot/` 的规则是"不与 Worker 共用的机器人运行入口放这里"，与实际（有两个文件被 Worker 共用）相反。
- 上帝文件仍在：`src/style.css` 2639 行、[form.mjs](lib/form.mjs) 1664、[convert-curriculum.js](scripts/convert-curriculum.js) 1559、[renderer.mjs](lib/renderer.mjs) 1336、[generate-data.js](scripts/generate-data.js) 1335、[oauth.mjs](workers/oauth.mjs) 1215。

**影响**：边界规则的权威性被自己削弱——下一个人看到 `workers/ → bot/` 会照抄，而看到 `bot/` 的规则又会以为不该这么写。`oauth.mjs` 越像工具箱，"新能力该放哪"的答案就越模糊。

**建议**：

1. 把 `fetchCodeforcesAccepted` / `fetchLuoguProblems` / `fetchAtCoderAccepted` 与相关解析下沉到 `lib/` 或 `workers/services/`；`oauth.mjs` 只保留路由、鉴权与协议适配。
2. 决定 `bot/` 的边界并写进依赖图：要么把被 Worker 共用的两个文件移到 `lib/`，要么在 `REPOSITORY-STRUCTURE.md` 里画出 `workers/ → bot/` 并改掉那条规则。
3. `renderer.mjs` / `convert-curriculum.js` 按页面与来源拆分为独立模块（可分批，不必一次做完）。

### T4 · CI：一次 push 构建 2 次，PR 合并合计 3 次构建 / 2 次 Chromium 安装

**现状**：`deploy.yml` 有两个 job，`checks.yml` 在 PR 上又跑一遍同样的东西。

**证据**：

| 触发 | 工作 | 其中包含 |
| --- | --- | --- |
| PR → `checks.yml` | `npm run verify` + `playwright install --with-deps chromium` + `test:e2e:ci` | 构建 1 次 + Chromium 1 次 |
| push `main` → `deploy.yml` `build` | `npm run check`（= `verify`：语法 + reindex + 539 单测 + **构建**） | 构建 1 次 |
| push `main` → `deploy.yml` `browser-check` | `npm run build` + `playwright install --with-deps chromium` + `test:e2e:ci` | 构建 1 次 + Chromium 1 次 |

因此：**每次 push 到 `main`（包括每一名队员的每一次保存打卡）都构建 2 次**；如果这次 push 来自合并进来的 PR，同一个改动合计构建 **3 次**、安装 Chromium **2 次**（每次约 130 MB 下载）。

- `deploy.yml` 的 `build` job 的 `actions/setup-node` **没有** `cache: npm`，而同文件 `browser-check` job 有——同一份 `package-lock.json` 在一个 workflow 里被冷装一次、热装一次。

**影响**：CI 时间与失败面都翻倍；队员每次打卡触发的发布也走这条重路径（218 个 `save` 提交意味着这条路径被反复执行）。

**建议**：`deploy` 依赖 `checks` 的结论（或在 `deploy.yml` 里合并 job，让 build 的产物直接给 browser-check 用，而不是重新构建）；给 `build` job 补 `cache: npm`；把 Chromium 安装换成 cache 或只在 browser-check 装一次。预计可省掉一半以上的 CI 时间。

### T5 · 文档治理：447 KB / 21 篇，同一事实散落在 4–5 处

**现状**：`docs/` 已经比它描述的代码更难读。

**证据**：

| 文档 | 体量 |
| --- | --- |
| [HANDOFF.md](docs/HANDOFF.md) | 91 KB（纯时间追加，同时声明"不再是当前实现的单一权威"） |
| [SPECIFICATION.md](docs/SPECIFICATION.md) | 62 KB |
| 本文（PRODUCT-AUDIT.md） | 49 KB |
| [PROBLEM-AUDIT.md](docs/PROBLEM-AUDIT.md) | 44 KB（含对上一轮修复的逐条签收与残留项收口） |
| [PROJECT-HISTORY.md](docs/PROJECT-HISTORY.md) | 38 KB |
| [PROBLEM-ENRICHMENT-SPECIFICATION.md](docs/PROBLEM-ENRICHMENT-SPECIFICATION.md) | 31 KB |
| **`docs/` 合计** | **447 KB / 21 篇** + README 52 KB |

同一个事实（例如"当前 schemaVersion 是几""哪些路由已实现""测试有多少"）在 README、SPECIFICATION、HANDOFF、PRODUCT、各专项规格里各写一遍，而且**每一份都曾经至少失真过一次**——`PROBLEM-AUDIT.md` 的 22 条里有 6 条（第 8、9、10、11、12、13 条）就是文档内部/与代码互相矛盾。

**影响**：这已经成为**返工的直接来源**，不是可读性问题。任何新接手的人都要在 5 份文档之间做一致性推理，而推理成本随文档增长而上升。

**建议**：立一份 `docs/CURRENT-STATE.md`（**硬上限 10 KB**），只写三件事：① 现在是什么（数据结构、路由、各项能力的一句话状态）；② 什么是冻结的（`training/` v2、题面归档的维护模式）；③ 验收口径与当前基线数字。规则：

- **易变数字只允许出现在这一份里**（测试数、构建条数、覆盖率、字段采纳率）。其他文档一律引用它，不复制。
- 计划类内容（`PRODUCT.md`）与历史类内容（`HANDOFF.md`、`PROJECT-HISTORY.md`）移入 `docs/archive/` 或明确标注"历史快照，不反映当前实现"。
- 专项规格（`LEARNING-STATE-*`、`PROBLEM-ENRICHMENT-*`、`SUBMISSION-PAGE-*`）合并为一份"字段与接口契约"，避免每个功能一对 design/spec 文档。

### T6 · 目录契约有缺口，且与代码冲突

**现状**：[REPOSITORY-STRUCTURE.md](docs/REPOSITORY-STRUCTURE.md) 声称"根目录只保留项目配置、部署入口和这些一级职责目录"，但实际存在的一级目录里有若干不在契约中。

**证据**（对照当前根目录与两份文档）：

| 目录 | REPOSITORY-STRUCTURE | README 结构树 | 说明 |
| --- | --- | --- | --- |
| `oi-wiki/` | ❌ 缺失 | ❌ 缺失 | 被 `.gitignore` 明确标注为"外部同步资料"的一级目录，却不属任何契约 |
| `e2e/` | ✅ | ❌ | Playwright 测试目录 |
| `training/` | ✅ | ❌ | v2 冻结数据（README 全文零提及） |

**影响**：`oi-wiki/` 这种"合同外"目录会让"根目录约定"失去权威；`training/` 缺席 README 则与§3.1 的"计划与交付分叉"是同一个病。

**建议**：把 `oi-wiki/` 补进契约（一行说明来源与用途）；给 `e2e/`、`training/`、`build/` 在 README 结构树里各补一行；`artifacts/` 在冒烟脚本启动时清理自身产物（或每次运行覆盖同名文件），避免无限增长。

## 附录 B · 口径与已知偏差

1. **"使用率"是从数据后果反推的**，不是点击统计。对"需要用户主动做一次动作、但不在数据里留痕"的功能（导出、机器人、AI 概括），本文只能标"不可测"。
2. **题号是归并唯一题的唯一依据**（`problemKey`）。`其他` 平台的 11 条记录无题号，不计入 127 道唯一题，同题协作率因此略被低估。
3. **时间指标用中位数**：均值被补录样本拉偏（廖夏时滞均值 3.61 天 vs 中位 0.50 天）。
4. **首次/末次周不完整**：窗口起于 07-21（首周缺 1 天），末周 09-21→09-27 完整。趋势结论基于 08-10/08-17 的峰值与 09-14/09-21 的低位对比，不受边界影响。
5. **`logs/` 只覆盖 3 人 69 天**：任何"衰减"结论都是 2 个月的观测，不能外推为长期留存结论。
