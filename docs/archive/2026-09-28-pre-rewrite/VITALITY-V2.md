# 活力 v2：算法修正与个人统计

2026-09-13。此文件覆盖 VITALITY-DESIGN.md 中 v1 的算法、去重和展示契约。源日志与题数不迁移；构建派生数据带 `vitalityVersion: v2`。新旧活力值不可直接用作成长前后对比。

## 修复依据

真实库有 165 条带 Rating 的记录：洛谷 108、Codeforces 46、其他 11。旧版没有按平台排除记录，但新知识点的 θ=0.5 会让很多分数接近零；其他平台有 6 条四舍五入成零。旧版又以题名兜底去重、只取最强标签、同日按题名顺序更新能力，并把未知结果当完成，影响解释与公平性。

## 现行公式

```
θ0 = 800/213 + log(0.85/0.15) ≈ 5.4905
θ(g) = θ0 + (2400/213) × (1 − exp(−g/12))
P = sigmoid(θ − rating/213)
M = exp(−(P − 0.85)² / (2 × 0.20²))
C = 1 − exp(−mean_tag_gain/6)
M_eff = (1−C) × 0.5 + C × M
B = (rating/1600)^0.75 × M_eff
题目额度 = B × quality
```

`quality`：independent=1、hinted=0.7、editorial=0.5、unknown=0.6、unfinished=0.15。未知结果系数是历史兼容估计，不代表比看题解更独立。当前 v6 日志允许每题保存 `outcome`，活力计算会读取该字段；缺失值仍按 unknown，不从掌握自评推断结果。2026-09-26 审计快照中 193 条记录有 24 条带真实 outcome，其余 169 条为 unknown。v2 尝试事件尚未接入生产界面，因此当前以日志字段为权威；完成事件迁移并回填后，事件投影优先，日志字段只作为兼容快照。

区间记录的单题活力按覆盖天数等额分摊到每日曲线，总额度保持不变。`count` 热力图仍表示覆盖当天的训练记录数，可能因多条记录而大于 1；“训练日”指标只取日期并集，不把记录数当成天数。

证据不足时 C 小，以中性匹配度为主，不让未知能力直接触发极端惩罚。入门先验不等于宣称队员已掌握入门。θ 的饱和上限扩大到约 16.76，避免旧上限 9.5 让目标难度永远停在约 1700。`optimalRating` 保留为知识点级纯函数；页面不再用历史最大 θ 冒充当前个人目标。

能力更新按 `1.5 × (rating/1600)^0.75 × learning_quality`，多标签去重后均摊；各标签能力平均后用于匹配。已完成或历史未知采用相应折算，unfinished 的 learning_quality=0。仍保留两周免衰减、最低 50% 的遗忘规则。重复记录不重复增加增益，也不靠重新提交刷新证据日期。同日所有题使用日初证据，然后统一更新，未来新增记录不会倒灌历史分数。

这些系数是工程选择，并非经过个体结果数据验证的预测模型。当前未解决标签粒度差异、跨平台换算误差、无题号重复无法识别等限制。

## 身份、结算和守恒

题号可靠时按成员 + canonicalProblemKey 聚合；否则用成员 + 日期 + 永久记录 ID。不同平台同名题不自动合并，也不猜测无题号的同题关系。

同题首次有有效 Rating 的记录冻结难度、匹配度和能力基准。首次缺难度不占计分名额。再次记录若完成质量未提高则为 duplicate；若从未完成变成完成，只结算新额度与已结算额度之差。例如首次 0.15B，后续独立完成补 0.85B。review/practice 明确不计分。去重位于算法而非构建前过滤，避免吞掉后续完成。

每条派生记录有 `vitalityStatus`（counted/completed_delta/duplicate/review/missing_rating）和 `vitalityOutcome`。按记录四舍五入到千分位后，成员、日曲线、平台、热力图和全队从同一份数值相加。所有有记录日期保留，包括当天只有重复题的零增量日期。纠错、删除或算法升级会重算历史；“单调”仅指一次有效快照中的累计曲线，不承诺跨版本或删改不下降。
