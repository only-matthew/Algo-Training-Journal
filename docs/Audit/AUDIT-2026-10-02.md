## 2. 严重问题（P0）

### 2.1 `[实测]` 题面解析正则二次复杂度，单请求打满 Worker CPU

**证据**
- `workers/services/problem-statement.mjs:35` — `const tokens = /<!--[\s\S]*?-->|<![^>]*>|<\/?[A-Za-z][^>]*>|[^<]+|</g;`
- `workers/services/problem-statement.mjs:59` — `const MARKDOWN_IMAGE = /!\[([^\]]*)\]\(\s*([^\s)]+)(?:\s+(?:"[^"]*"|'[^']*'|\([^)]*\)))?\s*\)/g;`
- 入口：`workers/oauth.mjs:208`（`readJsonBody(request, 2 MiB + 4 KiB)`）与 `:219-221`（客户端回传的 `html` 直接进解析器，不再请求上游）

**问题**：两个正则对"只有半个标签/半个图片语法"的输入会退回逐位置重试，复杂度约 O(n²)。实测：39 KB 的 `"<a"` 重复串耗时 0.55 s、78 KB 耗时 2.23 s、156 KB 耗时 11.1 s；图片正则同量级（78 KB 耗时 2.5 s）。按二次增长外推，2 MiB 上限的请求需要数十分钟 CPU——远超 Cloudflare 的 CPU 预算，请求会被杀掉，同时阻塞同一 isolate 上的其他请求（包括队友的日志写入）。

**触发条件**：任一白名单成员（或会话被窃者）POST `/api/problem-statement`，body 形如 `{"platform":"Codeforces","problemNumber":"1A","html":"<a<a<a…"}`。已有的 10 次/分钟限流挡不住"单个请求就烧满预算"，而且限流表还是 isolate 内存态（`workers/oauth.mjs:23-26`）。

**修复建议**：
1. 把 `:35` 的词法扫描换成手写线性扫描（`indexOf(">")` 逐段推进），不要用回溯型正则；
2. `:59` 的图片语法改为手写扫描，并对未闭合的 `![` 设长度上限（例如超过 512 字节仍未闭合即放弃该候选）；
3. 入口处加解析时限（`oauth.mjs:219` 之后包一层预算），超时返回 422 而不是让 isolate 被杀。

**验收判据**：新增用例断言 `"<a"×100000` 与 `"!["×100000` 的解析在 200 ms 内返回。

### 2.2 `[静态]` 网页保存会静默丢弃审计字段（真实数据损失）

**证据**
- 落盘白名单：`lib/log-schema.mjs:216-232` — `metaFromProblems` 只取 `id, name, problem, platform, problemNumber, difficulty, difficultyRating, tags, reviewDue, fileIndex, blocker`，再叠加 `normalizeLearningState` 与 `storedEnrichment`（后者经 `lib/problem-enrichment-schema.mjs:141-152`，白名单只有 5 个富化字段）。
- 两条写路径都会重写整天 `meta.json`：
  - v2 保存：`workers/services/logs-v2.mjs:240` → `metaFromProblems`
  - 旧接口/单题复习 PATCH：`workers/routes/logs-v2.mjs:33-45` → `workers/services/legacy-logs.mjs:134`（`validateLogInput`）→ `:147` `planLogChanges` → `workers/services/log-planning.mjs:39` → `metaFromProblems`
- 真实数据里这些字段大量存在：`logs/郭一鸣/2026/08/05/meta.json:14`（`"problemNumberLegacy": "1114A"`）、`logs/郭一鸣/2026/09/08/meta.json:15,17`（`difficultyLegacy` / `difficultyRatingSource`），全仓库 `meta.json` 中命中 250 处以上。
- 文档已自认此问题：`docs/HANDOFF.md:885` —「`difficultyLegacy` / `difficultyRatingSource` 等审计字段不在 Schema 白名单里，队员通过网页编辑某天记录后这些字段会消失」。

**问题**：白名单不在表里的字段一律消失。改一道题的复习状态会重写该日**所有**题目，因此一次点击即丢掉当天每一道题的难度来源与题号原值。HANDOFF 只把它记成"表单路径"的问题，实际上单题复习 PATCH 路径同样中招且危害更隐蔽（用户完全不觉得这次操作会改难度信息）。数据本身是回滚依据（`scripts/backfill-rating.mjs:158-160` 写入的原始难度与来源），丢了无法从当前值反推。

**修复建议**：
1. 在 `metaFromProblems` 里显式透传 `difficultyLegacy` / `difficultyRatingSource` / `problemNumberLegacy`（`difficultySource` 也应一并确认）；
2. 更彻底：把白名单改成"显式黑名单 + 未知字段透传"，避免下一个新增字段重蹈覆辙；
3. 加一条 round-trip 测试：`metaFromProblems(normalizeMeta(原始 meta).problems)` 必须保留全部审计字段；
4. 已丢失的历史数据无法恢复——本次审计确认 `logs/廖夏/2026/10/02/meta.json` 等较新记录已无这些字段，可先用 `git log -p` 核对哪些日期的字段是被哪次网页保存清掉的。

## 3. 高优先级（P1）

### 3.1 `[静态]` "今天"有三套定义，其中两套在同一个前端 bundle 里

- `lib/constants.mjs:28-33` `toDateString` 用 `getFullYear/getMonth/getDate`——**运行环境本地时区**；
- `lib/renderer.mjs:237`、`:376` 用它判断复习队列是否到期；
- `lib/form.mjs:1249`、`:1722`、`workers/routes/training-v2.mjs:26`、`workers/services/logs-v2.mjs:289`、`workers/oauth.mjs:165` 用 `toUtc8`；
- `lib/qq-message.mjs:6-11` 第三套：UTC+8 但日界在 04:00；`lib/review-utils.mjs:16-20` 的 `dueDateInDays` 注释声称 UTC+8，实现却是本地时区（`date.setDate` + `toDateString`）；
- 构建期同样分裂：`scripts/generate-data.js:68` 用 `toUtc8`，`:857`（掌握度基准日）与 `:1216`（复习队列过滤）用本地时区。

**影响**：非 UTC+8 环境的用户在 00:00–08:00（北京）之间会看到首页说"今天到期"而后端认为那是明天，一键顺延写进的日期与表单默认值（`addDaysToDate`，UTC 口径）也可能差一天。CI 跑在 UTC，`generate-data.js` 里两套口径会让本地构建与 CI 构建产出不同的 `overview.json`。

**建议**：`lib/constants.mjs` 只保留一个 `todayUtc8(now, boundaryHour = 0)`，把本地语义的 `toDateString` 改名（如 `localDateString`）并在业务代码禁用；顺带删掉 `dueDateInDays` 统一走纯字符串的 `addDaysToDate`。**验收判据**：`TZ=UTC npm run build` 与 `TZ=Asia/Shanghai npm run build` 产出的 `site/data/overview.json` 逐字节相同。

### 3.2 `[静态]` 同一天的写入有两条实现，产出字节不同

- `workers/services/log-planning.mjs:39` — `JSON.stringify(metaFromProblems(...), null, 2)`（**无尾随换行**）
- `workers/services/logs-v2.mjs:240` — `` `${JSON.stringify(...)}\n` ``（**有尾随换行**）

两条路径在同一天交替使用（PATCH 复习状态走旧接口，PUT 整天走 v2），而变更判定按 Git blob sha（`log-planning.mjs:51`），因此来回切换必然产生"只差一个换行"的提交，并打乱客户端 `revision` 指纹。此外 `gitBlobSha`（`logs-v2.mjs:45-52` 与 `log-planning.mjs:9-18`）、日志根目录布局（`roots()` 与 `logRoots()`）、整天读取（`legacy-logs.mjs:181-204` `readLog` 与 `logs-v2.mjs:273-287` `decodeLog`）各复制一份。`logs-v2.mjs:63-69` 的注释已承认"两侧不一致会误删 PDF"，说明作者踩过这类坑，但只对路径做了共享。

**建议**：合并为单一的 `planDayFiles()` 与单一 `gitBlobSha`/`roots`，`meta.json` 序列化统一带尾随换行（与 `scripts/reindex-training.mjs:23-24` 的 `serialized()` 一致）；合并后跑一次全仓重写并单独提交。

## 9. 构建复核后的 P1 补修（2026-10-02）

复核发现 §8.1 的词法扫描修复没有覆盖结束标签的栈扫描：`"<div>".repeat(n) + "</bogus>".repeat(n)` 在公开解析入口下，n 为 10000 / 20000 / 40000 时分别耗时 257 / 1064 / 4638 ms。8 秒计时器不能中断同步计算，因此此前“解析 DoS 完成修复”的结论不充分。

补修在共享 HTML 建树入口限制最多 128 层开放元素，超过时返回 `parse-failed`。这使关闭标签扫描有固定上限，也在递归查找、取文本和 Markdown 渲染之前拒绝异常深度。正常的祖先关闭与不匹配结束标签语义保持不变；超过深度上限的页面会被拒绝。

新增四条公开入口回归：原 40000 组攻击、合法题面中的异常深度、100 层嵌套加 100000 个不匹配关闭标签、祖先关闭的正文语义。专项 51/51 通过；原攻击约 0.32 ms 返回，100 层攻击约 33 ms 完成且保留正文。Worker dry-run 打包通过；补修未部署。

补修最终验收：`npm run verify` 退出码 0，语法与 ESLint、训练索引、524 + 92 = **616 项单测**（无失败、无跳过）及 198 条日志站点构建全部通过；文档链接专项与 `git diff --check` 通过。
