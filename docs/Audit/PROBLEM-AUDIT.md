## 1. 审计结论

项目的主构建链路和单元测试整体稳定，但当前仍有两个应立即处理的安全问题：QQ 机器人 webhook 可以在缺少签名头时绕过验签；题面图片归档允许 Worker 请求任意 HTTPS 地址并自动跟随重定向。两项均在本机以生产函数重新实证，不只是静态推断。

除此之外，完整质量门禁目前会被 Worker 的本地构建缓存误伤；日志构建对同一日期的两种目录布局采用静默去重，存在丢记录风险。产品层面的下一阶段仍应围绕复习闭环推进，不建议继续扩大题库和平台解析范围。

## 3. 当前问题台账

### P0-1：QQ webhook 缺少签名头时绕过验签

- **状态**：已实证，未修复
- **位置**：`workers/qq-bot.mjs:155-162`，入口位于 `workers/oauth.mjs:268`
- **现象**：代码只在至少存在一个签名头时调用验签函数。两个签名头都缺失时，请求直接进入事件处理。
- **本轮复现**：向生产处理函数传入无签名的 `op: 0` 请求，返回 `200` 和 ACK，且 `ctx.waitUntil` 被调用一次。
- **影响**：公网调用者可构造机器人事件；对受支持的消息类型，可进一步消耗机器人凭证、群消息能力与 AI 服务额度。
- **修复要求**：`QQ_BOT_SECRET` 已配置时，缺少任一签名头或验签失败都返回 `403`。增加“两个头都缺失”“只缺一个头”“合法签名”三类入口测试。

### P0-2：题面图片归档可请求任意 HTTPS 地址并跟随重定向

- **状态**：已实证，未修复
- **位置**：`workers/services/problem-statement.mjs:66`、`:233`
- **现象**：`safeImageUrl` 只校验 HTTPS 和非空主机名；下载使用 `redirect: "follow"`，没有来源域名限制，也不复核跳转后的目标。
- **本轮复现**：向 `archiveStatementImages` 提供 `https://untrusted.example/a.png`，生产函数确实调用该地址，下载参数为 `redirect: "follow"`。
- **影响**：已登录成员可通过回传页面源码等入口，让 Worker 请求攻击者指定的地址；响应内容还会作为归档图片返回，形成服务端请求代理。
- **修复要求**：为已支持平台建立明确的图片域名白名单；改用手动重定向，每一跳重新检查协议、主机和跳转次数；补充含 `<img>` 的客户端回传测试。

### P1-1：完整质量门禁被忽略目录中的生成代码阻断

- **状态**：已实证，未修复
- **位置**：`eslint.config.mjs:4`；生成目录为 `workers/.build-cache/worker-dryrun/`
- **现象**：ESLint 配置扫描 `workers/**/*.{js,mjs}`，但没有忽略 `.build-cache`。本轮 `npm run verify` 在 lint 阶段报告 8 个 `no-unused-vars` 错误并提前退出。
- **影响**：开发者运行 Worker 本地构建后，正常源码即使没有问题也无法通过门禁；后续测试和构建不会执行。
- **修复要求**：在 ESLint 配置中统一忽略 `**/.build-cache/**`、`site/**`、`build/**` 等生成目录，并增加一个配置级回归检查，确保忽略目录不会重新进入扫描范围。

### P1-2：同日两种目录布局并存时可能静默丢记录

- **状态**：已核对；上一轮已做完整复现，本轮源码逻辑未变
- **位置**：`scripts/generate-data.js:153`、`:193`
- **现象**：构建同时识别 `YYYY-MM-DD` 与 `YYYY/MM/DD`，最后按 `${member}|${date}|${problemIndex}` 去重。去重既不比较稳定题目 ID，也不报告冲突。
- **影响**：两套目录并存时，一份记录可被无提示丢弃；构建仍成功，使用者难以及时发现。
- **修复要求**：发现同成员同日期存在两种目录时直接失败并给出路径；完成迁移后再考虑删除旧布局读取逻辑。若仍需合并，必须按稳定 ID 或完整内容判重，冲突不得静默选择。

### P1-3：OAuth 握手与成员边界缺少入口级回归测试

- **状态**：已核对，未补测试
- **位置**：`workers/oauth.mjs:120-157`、`:104-119`
- **缺口**：没有覆盖缺失、错误和过期 OAuth state，站外 `returnTo`，非白名单用户，以及会话成员与配置目录不一致等关键分支。
- **影响**：认证与成员隔离逻辑发生回归时，现有测试可能继续全绿。
- **修复要求**：围绕公开入口构造请求，断言状态码、跳转地址、cookie 生命周期和目录所有权；避免只用内部 `seal()` 伪造已登录状态。

### P2-1：大型模块继续增长，变更影响面偏大

- **状态**：已量化，属于维护性问题
- **规模**：`lib/form.mjs` 约 1664 行，`lib/renderer.mjs` 约 1344 行，`scripts/generate-data.js` 约 1347 行。
- **影响**：提交表单、页面渲染与站点生成各自集中在单文件中，局部修改需要理解大量无关状态，也让行为测试更难落到清晰边界。
- **建议**：安全与正确性问题修复后再拆分。优先抽离表单的题面导入/AI 分析、渲染器的页面级模块，以及构建脚本的日志读取、预渲染和产物发布阶段。每次只移动一个职责并保持现有导出兼容。

## 4. 产品改进方向

当前产品文档已经把目标收敛为“选题 → 做题 → 记录 → 复习 → 重做”。下一步最有价值的产品改进是让完成结果自动产生可解释、可取消的复习建议：提示后完成、看题解完成和未完成默认建议三天后复习；独立完成不强制安排；用户可以改期或关闭。

复习时应创建一次新的尝试记录，并在同题详情中并列显示日期、完成结果、卡点与心得。这样才能计算真实的到期重做率，并判断复习功能是否有效。完整课程库、更多平台解析和新题单来源可继续作为维护能力，但不应先于这条闭环。
