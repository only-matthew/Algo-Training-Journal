# 一万条训练记录容量设计

本轮容量目标是累计 10,000 条训练记录时，普通访问不下载全量数据，日常新增记录不重写全部题目产物。

## 数据契约

- `data/overview.json`：首页近 30 天摘要、统计，以及最多 100 条到期复习。
- `data/manifest.json`：唯一分片目录，记录月份、成员年度分片、错题集合地址和数量。
- `data/logs/YYYY-MM.json`：分析页的月份分片。
- `data/members/<成员>/YYYY.json`：成员历史的年度分片。
- `data/review.json`：错题与复习记录集合。
- `data/tag-index.json`：标签摘要；`data/tags/<标签>.json`：单标签记录。
- `data/problems/<成员>/<日期>/<题目ID>.json`：完整单题数据。

浏览器缓存已经请求过的分片。分析范围变化时只加载覆盖月份；成员页不读取其他成员数据；错题本不扫描普通记录。大型列表每次只创建 40 个条目。

## 增量构建

`.build-cache/site-state.json` 保存重型输出的内容指纹。题目详情 HTML、题目 JSON 和成员页只有在源记录、关联记录、活力数据或页面壳变化时才重建。删除记录后，状态清单会移除对应旧文件；日志、成员和标签分片也会清理不再出现在新 manifest 中的文件。

这里采用的是“全量扫描轻量元数据、增量生成重型产物”，不能把每条日志当成互不相关的孤岛。每次构建仍会遍历全部摘要，重算同题索引、标签反向索引、知识树覆盖和统计；这些线性内存计算在 10,000 条规模成本可控。题目页指纹包含完整的同题关联列表，标签页指纹包含该标签的记录与知识节点，因此新增一条日志时，旧的同题页面和相关标签页面也会正确失效并重建。

相同输入连续构建应报告全部重型产物 `reused`、零 `rebuilt`。代码或页面壳变化会重建 HTML；只修改一题时，应主要重建该题、同题关联页、所属成员页和聚合分片。

## 验收边界

- 生产产物不存在 `data/all.json`。
- 首页数据量不随全部历史记录线性增长。
- 默认分析页只请求当月分片。
- 成员、分析、错题列表不会一次创建超过 40 张记录卡片。
- 标签索引不内嵌记录数组。
- 连续两次无改动构建的重型输出为零重建。
- 源记录删除后，对应题目 HTML 与详情 JSON 不再存在。
- 新增同题记录后，既有同题页面的关联区同步更新；新增或移除标签后，对应标签页同步更新。

每道题仍保留可直接阅读的静态 HTML，但题目页使用独立轻量壳，不再重复携带首页、分析页、知识地图和提交工作区。标题、canonical、Article JSON-LD、正文、同题链接和标签链接仍在首屏 HTML 中；代码高亮、公式、导出与本人编辑/复习操作由独立浏览器入口增强。

2026-09-21 在 Docker（4 CPU、4 GiB）中以 10 名成员 × 1,000 条记录验证：冷构建约 40.2 秒，热构建约 11.7 秒；20,420 个发布文件共约 388 MiB，其中 10,000 个题目 HTML 共 133.1 MiB、平均 13.6 KiB。改单题题号并新增标签后约 12.3 秒，仅 92 个依赖产物重建；旧同题反链被移除，新标签反链同步生成。该结果低于 GitHub Pages 的 1 GiB 发布站点上限，并为附件增长留有余量。若未来继续增长到数万条以上，应再启用 sitemap 分卷，并重新核算附件与完整题目 JSON 的体积。
